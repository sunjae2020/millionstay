Sample 5 선정 기준 (booking.md 내에서 선정):

S1. 단순 GET (read-only, auth만)
    예: GET /api/v1/bookings, GET /api/v1/bookings/:id

S2. 복잡한 POST (다중 DB write + side effect)
    🎯 강력 추천: POST /api/v1/bookings/:id/confirm
    이유: CF-002 (booking→contract 정밀도 손실) + CF-014 (트랜잭션 
    부재) 두 P0/P1 finding이 모두 해당. 가장 위험한 endpoint를 
    sample로 다루면 포맷이 worst case 검증됨.

S3. Money-touching endpoint
    예: POST /api/v1/bookings/quote 또는 가격 계산 호출
    Money 컬럼 표기 + MONEY_AUDIT cross-ref 검증

S4. Audit log 누락 endpoint
    booking.md 내에서 logAction 호출이 없는 endpoint 1개 선정
    "⚠️ Missing logAction" 표기 패턴 검증 (CF-008 추적)

S5. 경계 케이스 (cross-ref 필요)
    nested route 또는 다른 도메인 cross-ref가 필요한 endpoint
    예: /api/v1/bookings/:id 가 contract를 트리거하는 케이스

중요한 건 **모든 패턴 커버**, booking.md 5개 고집 X.
