## SECTION 1. 플랫폼 소개 (4장)

### Slide 3 — MillionStay 한 문장 정의 ★
- **핵심 한 줄:** MillionStay는 **단기 숙소 · 장기 숙소 · 홈스테이**를 한 시스템에서 운영하는 부동산/숙박 관리 SaaS입니다.
- **본문:**
  - 학생·게스트, 호스트 가정, 유학원(에이전트), 집주인(오너), 서비스 파트너(청소·픽업)를 **하나의 플랫폼**에서 연결
  - 예약 → 계약(전자서명) → 결제 → 정산 → 문서보관까지 **전 과정 디지털화**
  - 핵심 가치: "흩어져 있던 숙박 운영 업무를 한 곳에서, 자동으로"
- **발표자 노트:** 우리는 단순 예약 사이트가 아니라 '운영 백오피스 + 고객 채널'을 통째로 제공한다는 점 강조.

---

### Slide 4 — 우리가 운영하는 3가지 상품 ★
- **핵심 한 줄:** 같은 시스템, 다른 운영 방식. 상품마다 흐름이 다릅니다.
- **본문 (3단 비교):**

| 상품 | 운영 방식 | 특징 |
|------|-----------|------|
| **홈스테이 (Homestay)** | 관리자가 직접 매칭 (중개형) | 학생 신청 → 운영팀 심사 → 승인된 호스트 가정과 매칭 → 전자계약 → 선불결제 → **매월 자동 청구** |
| **단기 숙소 (Short-term)** | 고객 셀프 예약 | 검색 → 공간 선택 → 결제 → 체크인/아웃 → 인보이스 발행 (주/월 단위) |
| **장기 숙소 (Long-term)** | 고객 셀프 예약 + 계약 | 단기와 유사하되 장기 계약서, 보증금(Bond)·선납금 포함 |

- **발표자 노트:** "홈스테이만 사람이 직접 매칭하고, 단기·장기는 고객이 스스로 예약한다"가 가장 큰 차이.

---

### Slide 5 — 플랫폼 구성 (직원이 알아야 할 화면들)
- **핵심 한 줄:** 하나의 백엔드(API) 위에 역할별 6개 웹 화면(포털)이 올라가 있습니다.
- **본문:**
  - **million-stay-web** (5173) — 게스트/학생용 (예약 검색, 홈스테이 신청, 내 예약·인보이스·문서)
  - **property-admin** (5174) — 운영팀(관리자)용 본진 (심사·매칭·결제·정산·CMS)
  - **agent-portal** (5175) — 유학원(에이전트)용 (학생 의뢰, 커미션 추적)
  - **owner-portal** (5176) — 집주인(오너)용 (입주율·수익 대시보드)
  - **service-host-portal** (5177) — 청소/픽업 파트너용 (작업 목록·일정·수입)
  - *(mockup-sandbox — 내부 프로토타입용, 고객 노출 X)*
- **발표자 노트:** "고객이 보는 화면 ≠ 우리가 일하는 화면". 운영팀은 주로 property-admin에서 작업. (포털 상세는 Section 3 참고)

---

### Slide 6 — 전체 그림 한눈에 (생태계 다이어그램) ★
- **핵심 한 줄:** 5명의 주체가 플랫폼을 중심으로 연결됩니다.
- **본문 (다이어그램용 구조 — 가운데 MillionStay, 주변 5개 노드):**
  - 학생/게스트 ──(신청·예약·결제)──▶ **MillionStay** ◀──(승인·매칭·정산)── 운영팀
  - 호스트 가정 ──(방 제공·학생 수용)──▶ **MillionStay**
  - 유학원 ──(학생 의뢰)──▶ **MillionStay** ──(커미션 지급)──▶ 유학원
  - 집주인 ◀──(입주율·수익 리포트)── **MillionStay**
  - 서비스 파트너(청소·픽업) ◀──(작업 배정)── **MillionStay**
- **발표자 노트:** 이 그림 한 장이 오늘 교육의 핵심 지도. 이후 슬라이드는 각 화살표를 자세히 보는 것.

## SECTION 2. 기존 플랫폼과의 차이점 (2장)

### Slide 7 — 기존 홈스테이·쉐어 플랫폼의 한계 ★
- **핵심 한 줄:** 기존 방식은 "연결만" 하고 끝납니다. 운영은 사람이 수기로.
- **본문 (기존의 문제):**
  - 단순 리스팅/매칭만 제공 → 계약·결제·정산은 이메일·엑셀·수기 처리
  - 학생-호스트 매칭이 **주관적**이고 근거 기록이 없음
  - 미성년 학생 보호(WWCC 등) 컴플라이언스가 시스템에 없음
  - 매월 월세 청구를 사람이 일일이 챙김 → 누락·연체 발생
  - 유학원 커미션 계산이 수작업 → 분쟁·지연
  - 문서(여권·계약서)가 여기저기 흩어져 개인정보 리스크
- **발표자 노트:** 청중에게 "기존에 이런 거 겪어봤죠?" 공감 유도.

---

### Slide 8 — MillionStay가 다른 점 ★
- **핵심 한 줄:** 매칭부터 정산까지 **한 시스템에서 자동으로**, 근거를 남기며.
- **본문 (Before → After 대비):**

| 구분 | 기존 플랫폼 | MillionStay |
|------|-------------|-------------|
| 매칭 | 사람이 감으로 | **점수 기반 매칭 엔진** + AI 매칭 근거 설명 |
| 계약 | 종이/이메일 | **전자서명**(서명 이미지·IP·타임스탬프 감사기록) |
| 결제 | 수기 송금 확인 | **Stripe 선불 + 매월 자동 청구**(구독) |
| 미성년 보호 | 없음 | **WWCC 검증을 매칭 필수 조건**으로 강제 |
| 커미션 | 엑셀 계산 | **자동 정산 원장**(발생→승인→지급 추적) |
| 부가서비스 | 별도 외주 관리 | **픽업·청소를 플랫폼 내 배정·추적**(사진·상태) |
| 문서 | 흩어짐 | **암호화 보관 + 보존기간 자동관리**(호주 개인정보법) |
| 3개 상품 | 따로 운영 | **하나의 시스템에서 공통 운영** |
- **발표자 노트:** 핵심 메시지 = "우리는 연결 + 운영 자동화 + 컴플라이언스를 함께 제공."

## SECTION 3. 사용자 역할 & 포털 소개 (7장)

### Slide 9 — 플랫폼을 쓰는 5명 (+운영팀) ★
- **핵심 한 줄:** 각 역할은 자기 전용 포털과 권한(JWT)을 가집니다.
- **본문:**
  - 🎓 **학생/게스트** — 신청·예약·결제·문서열람·고객문의 → million-stay-web
  - 🏠 **호스트/집주인(오너)** — 가정·매물 등록·정산수령 → owner-portal
  - 🎫 **유학원(에이전트)** — 학생 대신 신청·커미션 추적 → agent-portal
  - 🚗 **서비스 파트너** — 청소/공항픽업 작업 처리·수입 → service-host-portal
  - 🛠 **운영팀(관리자)** — 위 모든 것을 심사·매칭·정산·관리 → property-admin
- **발표자 노트:** 권한이 분리돼 있어 "오너는 세입자 실명을 못 본다" 같은 개인정보 보호가 설계에 내장됨. 다음 슬라이드부터 포털을 하나씩 투어.

---

### Slide 10 — 포털 한눈에 보기 (요약표) ★
- **핵심 한 줄:** 누가, 어떤 주소로, 무엇을 하는지 한 장 정리.
- **본문:**

| 포털 | 사용자 | 포트 | 로그인 방식 | 핵심 기능 | 언어 |
|------|--------|------|-------------|-----------|------|
| **million-stay-web** | 학생/게스트 | 5173 | 게스트(이메일+PW) | 검색·예약·홈스테이 신청·내 예약/인보이스/문서 | EN·JA·KO·TH·VI·ZH |
| **property-admin** | 운영팀 | 5174 | 관리자 | CRM·매칭·예약·결제·정산·CMS 전체 | EN·JA·KO·TH·ZH |
| **agent-portal** | 유학원 | 5175 | 파트너 | 의뢰 예약·커미션 추적 | EN·JA·KO·TH·ZH |
| **owner-portal** | 집주인/호스트 | 5176 | 파트너 | 입주율·수익·매물·랜딩사이트 | EN·JA·KO·TH·ZH |
| **service-host-portal** | 청소·픽업 파트너 | 5177 | 파트너 | 작업·일정·수입 | EN·JA·KO·TH·ZH |

- **발표자 노트:** 게스트 포털만 베트남어(VI) 추가 지원. 파트너 3종은 동일한 5개 언어.

### Slide 11 — 포털① 게스트/학생 (million-stay-web)
- **핵심 한 줄:** 고객이 처음 만나는 얼굴 — 공개 사이트 + 로그인 후 내 포털.
- **본문:**
  - **로그인:** 이메일+비밀번호 (게스트 JWT) / 회원가입·비밀번호 찾기
  - **공개 영역:** 홈, 검색, 공간 상세, 예약(결제), 블로그, 소개/문의/FAQ, 개인정보처리방침, (학생·에이전트·호스트용 랜딩)
  - **내 포털(`/portal`):** 내 예약, 예약 상세, 인보이스, 영수증, 문서, 결제수단, 프로필, **내 정보 다운로드(My Data)**, 고객문의(CS)
  - 통화 변환·AI 채팅 위젯·홈스테이 전용 서브도메인(homestay.millionstay.com) 지원
- **발표자 노트:** "내 정보 다운로드(My Data)"는 개인정보 열람·삭제 요청권 기능 — CS 문의 시 안내.

---

### Slide 12 — 포털② 운영팀 (property-admin) ★
- **핵심 한 줄:** 운영팀의 본진 — 거의 모든 업무가 여기서 일어납니다.
- **본문 (좌측 사이드바 주요 섹션):**
  - **ACCOUNT** — 연락처/거래처, 리드, **홈스테이 신청·학생요청·배치**, 태스크
  - **CS** — 고객문의 티켓
  - **PROPERTY** — 매물·공간·옵션·정책·사진 일괄업로드
  - **BOOKING** — 예약·계약·**서비스 호스트(파트너) 관리**
  - **PRODUCTS** — 숙박 상품·서비스·프로모션
  - **DOCUMENTS** — 문서·견적·인보이스·영수증·템플릿·홈스테이 청구
  - **FINANCE** — 인보이스·영수증·**커미션**·정기결제·환율·전표
  - **CONTENT** — 블로그·웹사이트 페이지(CMS)·번역
  - **AI ASSISTANT** — 챗봇 설정·지식베이스·대화이력
  - **SETTINGS** — 조직·사용자·계약유형·결제정보·API키·이메일/문서 템플릿
- **발표자 노트:** 대시보드는 예약/재무/운영 3개 탭. 신규 직원은 ACCOUNT·BOOKING·CS부터 익히면 됨.

---

### Slide 13 — 포털③ 유학원 (agent-portal)
- **핵심 한 줄:** 학생을 의뢰하고 커미션을 추적하는 파트너 포털.
- **본문:**
  - **로그인:** 파트너 JWT (이메일+PW) / 신규 에이전트는 `/apply`로 회사 등록 신청
  - **메뉴:** 대시보드 / 내 예약(My Bookings) / 매물(Properties) / **커미션(Commission)** / 고객지원
  - **주요 기능:** 본인이 의뢰한 예약만 표시(필터), 예약 상세에서 커미션 금액 확인, 커미션 내역(건별·상태·지급이력), 홍보용 매물 목록 열람
  - **마스킹:** 내부 원가·서비스 파트너 이름·일부 홈스테이 데이터는 **에이전트에게 비표시**
- **발표자 노트:** 에이전트는 "내 의뢰 + 내 커미션"만 봄. 다른 에이전트 데이터는 못 봄.

---

### Slide 14 — 포털④ 집주인/호스트 (owner-portal)
- **핵심 한 줄:** 매물 수익과 입주율을 셀프로 관리하는 포털.
- **본문:**
  - **로그인:** 파트너 JWT / 신규는 `/apply`로 매물·계좌 등록
  - **메뉴:** 대시보드 / 매물(Properties) / **입주현황(Bookings/Occupancy)** / **수익(Revenue)** / 사이트(Site) / 문의(Inquiries) / 고객지원
  - **주요 기능:** 입주율·당월수익·예정 체크인 한눈에, 매물별 상세(편의시설·요금·정책·입주 캘린더), 6개월 수익 추이, **{slug}.millionstay.com 전용 랜딩사이트** 빌더, 임차 문의 관리
  - **마스킹:** 세입자 실명은 운영팀만 열람(오너에게는 마스킹), 서비스 파트너 정보 비표시
- **발표자 노트:** 홈스테이 호스트도 이 포털 계열에서 매물/정산을 관리. 개인정보 마스킹이 핵심.

---

### Slide 15 — 포털⑤ 서비스 파트너 (service-host-portal)
- **핵심 한 줄:** 청소·픽업 기사가 배정받은 작업을 처리하는 포털.
- **본문:**
  - **로그인:** 파트너 JWT / 신규는 `/apply`로 서비스 파트너 신청
  - **메뉴:** 대시보드 / **내 작업(My Jobs)** / 일정(Schedule, 캘린더) / **수입(Earnings)** / 고객지원
  - **주요 기능:** 배정 작업 목록, 작업 상세 + **사진 최대 10장 업로드(증빙)**, 캘린더 일정, 서비스종류별·예약별 수입 집계
  - **마스킹:** 서비스 작업은 **학생·에이전트에게 비표시** (운영팀+해당 파트너만)
- **발표자 노트:** 다음 Section 7에서 픽업 드라이버 예시로 이 포털 흐름을 자세히 다룸.

---

## SECTION 4. 학생(고객) 워크플로우 (4장)

### Slide 16 — 학생 여정 전체 흐름 ★
- **핵심 한 줄:** 신청 → 서명 → 매칭대기 → 계약 → 결제 → 입주 → 자동 월청구
- **본문 (홈스테이 기준 상태 흐름):**
  - `신청서 작성(Draft)` → `제출(Submitted)` → `운영팀 심사(UnderReview)` → `매칭중(Matching)` → `매칭 제안(Proposed)` → `확정(Confirmed)` → `입주완료(Placed)` → `종료(Completed)`
- **발표자 노트:** 각 단계마다 학생에게 이메일이 자동 발송됨. 학생은 포털에서 현재 단계 확인 가능.

---

### Slide 17 — ① 신청 & 전자서명
- **핵심 한 줄:** 학생이 온라인 폼을 채우고 그 자리에서 서명합니다.
- **본문:**
  - 개인정보 + 선호조건(지역·학교·식사플랜·예산·입주일·기간) 입력
  - **미성년자(만 18세 미만)**: 보호자 정보 + **보호자 동의** + 보호자 함께 서명
  - 이용약관(T&C) 동의 시각 기록
  - `/sign/:token` 페이지에서 **캔버스 서명패드**로 서명 → 브랜드 PDF 자동 생성
  - 서명 PDF는 **Cloudinary 비공개 보관**, 학생·보호자·운영팀에 이메일 발송
- **발표자 노트:** 서명에는 IP·접속기기·시각이 함께 기록되어 법적 증빙이 됨.

---

### Slide 18 — ② 매칭 제안 & 계약
- **핵심 한 줄:** 운영팀이 매칭한 호스트를 학생이 확인하고 본계약에 서명합니다.
- **본문:**
  - 운영팀이 매칭 → 학생에게 "홈스테이 매칭을 찾았어요" 이메일
  - 학생이 호스트 프로필(가정 정보·식사·집 특징) 확인
  - **배치 계약서(Placement Agreement)** PDF 생성 → 학생(+보호자) & 호스트 양측 서명
  - 양측 서명 완료 → 결제 단계로 이동
- **발표자 노트:** 단기·장기는 이 매칭 단계가 없고 고객이 바로 예약. 홈스테이만 이 과정 존재.

---

### Slide 19 — ③ 결제 & 입주 후 ★
- **핵심 한 줄:** 선불 1회 결제 후, 월세는 자동으로 빠져나갑니다.
- **본문:**
  - **선불 결제** = 배치비(셋업) + 보증금(Deposit) + 첫 달 월세
    - 카드 결제 시 2% 수수료 / 계좌이체 시 수수료 0%
  - 결제 완료 → 배치 상태 `활성(Active)`, 학생 `입주완료(Placed)`
  - **매월 자동 청구**: Stripe 구독으로 월세 자동 결제 (크론잡이 청구일에 처리)
  - 학생 포털에서: 내 예약/배치, 인보이스 다운로드, 문서 열람, 고객문의(이미지 첨부), 내 정보 다운로드(개인정보 열람권)
- **발표자 노트:** 결제 실패 시 PastDue 상태가 되고 운영팀이 리마인더 발송. CS 문의 시 여기 확인.

---

## SECTION 5. 호스트 & 홈스테이 호스트 워크플로우 (3장)

### Slide 20 — 호스트 가정 등록 흐름 ★
- **핵심 한 줄:** 가정 신청 → 심사 → 승인 → 랜딩 활성화 → 학생 수락
- **본문 (상태 흐름):**
  - `제출(Submitted)` → `심사중(UnderReview)` → `(서류요청 DocsRequested)` → `승인(Approved)` / `반려(Rejected)`
  - 승인 즉시 시스템이 **property + 방(space) 자동 생성** (호스트가 랜딩 활성화 전까지 비공개)
  - 호스트는 **제출 즉시 포털 접근 가능** (승인 기다릴 필요 X)
- **발표자 노트:** 호스트는 승인 전에도 포털에서 서류 업로드 등 진행 가능.

---

### Slide 21 — 호스트가 하는 일
- **핵심 한 줄:** 가정 정보 등록, 컴플라이언스 서류, 학생 수락이 핵심 업무.
- **본문:**
  - **신청서 작성**: 가족 구성원, 방 정보, 식사 제공(Full/Partial/Dinner), 흡연·반려동물 여부, 집 특징(수영장·와이파이 등)
  - **WWCC 제출**: 18세 이상 모든 거주자의 아동안전체크(Working with Children Check) 업로드 → 미성년 학생 매칭의 **필수 조건**
  - **랜딩 활성화**: 승인 후 가정 페이지를 켜면 검색에 노출
  - **학생 수락**: 매칭 제안 이메일 받음 → 학생 프로필 확인 → **수락/거절**
  - **정산 정보**: 승인 후 계좌정보 입력(개인정보 보호 위해 사후 수집), 결제 내역 확인
- **발표자 노트:** 호스트가 수락해야 다음 단계(계약·결제)로 넘어감. 수락 지연이 병목이 될 수 있음.

---

### Slide 22 — 호스트 상태 흐름 (매칭~정산)
- **핵심 한 줄:** 제안 → 호스트 수락 → 결제대기 → 활성 → 종료
- **본문 (배치 Placement 상태):**
  - `제안(Proposed)` → `호스트수락(HostAccepted)` → `결제대기(AwaitingPayment)` → `활성(Active)` → `종료중(Ending)` → `완료(Completed)`
  - 예외 상태: `취소(Cancelled)` / `해지(Terminated)` / `연체(PastDue)`
  - 배치 생성 시 호스트의 수용 가능 인원(capacity) 자동 차감
- **발표자 노트:** CS/운영팀이 호스트 문의 받을 때 "지금 어느 상태인지"를 이 흐름으로 파악.

---

## SECTION 6. 관리자(운영팀) 워크플로우 (5장)

### Slide 23 — 운영팀이 쓰는 곳: property-admin ★
- **핵심 한 줄:** 운영팀은 property-admin 한 곳에서 모든 것을 처리합니다.
- **본문 (핵심 업무 5가지):**
  - ① 심사 & 승인 (호스트·학생)
  - ② 홈스테이 매칭 콘솔
  - ③ 결제·인보이스·커미션 정산
  - ④ **서비스(청소·픽업) 배정 & 모니터링**
  - ⑤ 재무 대시보드 / 설정(템플릿·청구주기·CMS)
- **발표자 노트:** 신규 직원은 대부분 이 화면에서 일함. 다음 슬라이드부터 핵심 업무를 하나씩.

---

### Slide 24 — ① 심사 & 승인
- **핵심 한 줄:** 호스트 가정과 학생 신청을 검토해 승인/반려합니다.
- **본문:**
  - **호스트 심사**: 가정 정보·거주자·WWCC·식사·집 특징·서명 PDF 확인 → 승인 시 property/방 자동 생성
  - **학생 심사**: 신청 정보·선호조건·약관 동의 확인
  - 담당 직원(assigned_staff) 지정 → 책임 추적
- **발표자 노트:** 승인은 단순 클릭이 아니라 컴플라이언스 체크(WWCC 등) 확인 후 진행.

---

### Slide 25 — ② 매칭 콘솔 (핵심 업무) ★
- **핵심 한 줄:** 점수 기반 추천을 보고, 운영팀이 최종 호스트를 선택합니다.
- **본문:**
  - `매칭중` 상태 학생 선택 → **호스트 추천(Host Suggestions)** 실행
  - 시스템이 **필수조건(Hard) 통과 + 점수(0~100)** 로 호스트 랭킹 제시
    - **필수 제외 조건**: 성별 선호 불일치 / 미성년·성인 정책 / 반려동물 알레르기 / 흡연 / 정원 초과 / **WWCC 미검증(미성년 시)**
    - **점수 가산**: 위치, 식단, 식사플랜, 문화 배경, 집 편의시설
  - AI가 랭킹 근거를 설명해줌 (참고용, 최종 결정은 사람이)
  - 호스트 선택 → **배치(Placement) 생성** (입주일·배치비·보증금·월세·에이전트 지정)
- **발표자 노트:** 매칭 엔진은 "추천"이지 "자동 결정"이 아님. 사람이 반드시 검토.

---

### Slide 26 — ③ 결제·정산·커미션
- **핵심 한 줄:** 인보이스 발행, 결제 추적, 유학원 커미션을 관리합니다.
- **본문:**
  - **인보이스**: 견적(Quote) → 인보이스 전환 → 발송 → 결제(Stripe/계좌) → Paid/연체 추적
  - **홈스테이 결제**: 선불(배치비+보증금+첫달) → 월 자동청구 모니터링
  - **커미션 원장**: 결제 성공 시 자동 발생 → `대기(Pending)` → 운영팀 `승인(Approved)` → `지급(Paid)`
    - 계산식: 고정 추천비 + (기준금액 × 비율%), 에이전트별 플랜 설정 가능
- **발표자 노트:** 돈 관련 컬럼은 시스템에서 문자열로 저장됨 — 직원은 화면 숫자만 보면 됨(개발 주의사항).

---

### Slide 27 — ④ 서비스 배정 & 대시보드
- **핵심 한 줄:** 공항픽업·청소를 파트너에게 배정하고, 전체 지표를 모니터링합니다.
- **본문:**
  - **서비스 배정**(상세는 Section 7): 예약/배치에 서비스 추가 → 파트너 지정 → 작업이 파트너 포털에 표시 → 상태·사진 모니터링
    - ⚠️ 서비스 작업은 **학생·에이전트에게 비표시**(개인정보 마스킹)
  - **재무 대시보드**: 오늘 체크인/아웃, 활성 예약, 입주율(%), 당월 매출, 6개월 매출 추이
- **발표자 노트:** 오너/에이전트가 보는 대시보드는 권한별로 데이터가 마스킹됨.

---

## SECTION 7. 서비스 파트너 워크플로우 (픽업 드라이버·청소 등) (4장)

### Slide 28 — 서비스 파트너란? & 서비스 종류 ★
- **핵심 한 줄:** 청소·공항픽업 같은 부가서비스를 수행하는 외부 파트너입니다.
- **본문:**
  - **누구:** 청소 담당, 공항 픽업 드라이버, 초기 정착(Initial Settlement) 도우미 등
  - **서비스 종류(예):**
    - `공항 픽업(airport_pickup)` — 학생 도착 시 공항 → 숙소 이동
    - `초기 정착(initial_settlement)` — 도착 당일 장보기·생활 안내
    - `청소(cleaning)` / `린넨(linens)` / 기타 정기·일회성 서비스
  - **연결 방식:** 단기·장기 예약은 `예약 서비스`로, 홈스테이는 `배치 서비스`로 붙음 → 시스템이 동일하게 처리
  - **과금 시점(billing_trigger):** 예약 시 선불(at_booking) / 체크아웃 시(at_checkout) / 요청 시(on_request)
- **발표자 노트:** 서비스 정의는 운영팀이 서비스 카탈로그에서 관리. 종류는 확장 가능.

---

### Slide 29 — 픽업 드라이버 워크플로우 (예시) ★
- **핵심 한 줄:** 배정 → 정보 확인 → 일정 확인 → 픽업 수행 → 완료 처리(사진).
- **본문 (드라이버 입장에서 본 단계):**
  1. **작업 수신** — 운영팀이 픽업 작업을 배정하면 service-host-portal "내 작업(My Jobs)"에 표시
  2. **정보 확인** — 작업 상세에서: 예약/배치 번호, **픽업 날짜·시간(체크인일)**, 학생 이름, 도착지 주소, 공항/터미널 정보(메모), 금액
  3. **일정 확인** — 일정(Schedule) 캘린더에서 당일 픽업 일정 확인
  4. **픽업 수행 & 상태 갱신** — 작업을 `처리중(Processing)`으로 변경
  5. **완료 처리** — `완료(Completed)`로 변경 + **현장 사진 최대 10장 업로드**(증빙)
  6. **수입 반영** — 완료 작업 금액이 "수입(Earnings)"에 자동 집계
- **발표자 노트:** 청소도 동일한 흐름(작업 수신 → 처리 → 완료+사진). 픽업은 시간·항공편이 중요해 메모 확인 필수.

---

### Slide 30 — 작업 상태 흐름 & 수입 계산
- **핵심 한 줄:** 작업은 정해진 상태를 거치고, 수입은 작업 금액의 합으로 집계됩니다.
- **본문:**
  - **예약 서비스 작업 상태:** `활성(Active)` → `처리중(Processing)` → `완료(Completed)` (또는 `취소(Cancelled)`)
  - **홈스테이 배치 서비스 상태:** `대기(Pending)` → `배정(Assigned)` → `일정확정(Scheduled)` → `완료(Completed)` (또는 `취소`)
  - **수입(Earnings) 집계:**
    - **서비스 종류별** — 예: 청소 12건 $1,200 / 공항픽업 5건 $250
    - **예약별** — 예약번호·체크인일·서비스 목록·합계
    - 통화 AUD, 작업 단가의 단순 합 (별도 커미션 없음)
- **발표자 노트:** 서비스 파트너는 "건당 단가" 모델. 에이전트의 "커미션" 모델과 다름 — 혼동 주의.

### Slide 31 — 관리자 측 반영: 서비스 배정 워크플로우 ★
- **핵심 한 줄:** 픽업·청소 작업은 운영팀이 property-admin에서 배정하고 끝까지 추적합니다.
- **본문 (운영팀 단계별):**
  1. **예약/배치 열기** — BOOKING → 예약 상세 (또는 홈스테이 배치 상세)
  2. **서비스 추가** — "+ 서비스" 버튼 → 서비스명·종류·수량·단가·빈도·메모 입력 (예: 공항픽업, 도착일, $50)
  3. **파트너 지정** — 서비스 항목에 활성 서비스 파트너(드라이버/청소) 선택 → 작업이 해당 파트너 포털에 표시
  4. **상태·증빙 모니터링** — 파트너가 올린 상태 변경과 사진을 예약 상세에서 확인 (`활성→처리중→완료`)
  5. **정산 연결** — 완료 작업은 과금 시점(선불/체크아웃)에 따라 인보이스/청구에 반영
  - **서비스 파트너 관리:** BOOKING → "서비스 호스트(Service Hosts)"에서 파트너 등록·가용일·연락처 관리
  - ⚠️ 배정된 서비스 작업은 **학생·에이전트 화면에서 마스킹**(개인정보 보호)
- **발표자 노트:** "운영팀이 만든다 → 파트너가 수행한다 → 운영팀이 확인·정산한다"의 한 사이클. 픽업 누락은 학생 도착 사고로 직결되니 일정 재확인 강조.

## 부록 A. 실전 시나리오 (선택 슬라이드 / 실습용)

> 시간 여유 있을 때 또는 실습 세션용. 슬라이드로 빼거나 핸드아웃으로 배포 추천.

### 시나리오 1 — 호스트 가정 승인하기
1. property-admin → CRM → 홈스테이 신청 → `심사중` 필터
2. 호스트 'Sarah Chen' 상세 열람: 가정정보·거주자·WWCC·식사패키지·집특징·서명 PDF
3. WWCC 인증서 확인 (미성년 학생 매칭 시 필수)
4. 메모 입력 후 **승인** → property/방 자동 생성, 호스트 랜딩 활성화 가능

### 시나리오 2 — 학생을 호스트와 매칭하기
1. 홈스테이 학생요청 → `매칭중` 학생 'Yuki' 선택
2. 선호조건(지역·식사·예산·학교) 확인
3. **호스트 추천** 실행 → 점수 랭킹 확인 (예: Sarah 87점, James&Linda 72점)
4. 'Sarah Chen' 선택 → **배치 생성**(입주일·배치비·보증금·월세, 에이전트 지정)
5. 호스트가 포털에서 학생 확인 후 **수락** → 배치 `호스트수락`, 학생 `확정`

### 시나리오 3 — 결제 & 커미션
1. `호스트수락` → 배치계약서 PDF 생성 → 양측 전자서명 → `결제대기`
2. 학생이 선불 결제(배치비+보증금+첫달, 카드 시 2% 수수료)
3. 결제 성공 → 배치 `활성`, 학생 `입주완료`
4. 에이전트 의뢰 건이면 커미션 원장 자동 생성(대기) → 운영팀 승인 → 지급

### 시나리오 4 — 월세 자동 청구
1. 크론잡이 청구일에 `활성` 배치 조회
2. Stripe 구독 인보이스 발행(예: 월 AUD 500)
3. 결제 성공 → 결제기록 생성, 다음 청구일 자동 갱신
4. 종료 시까지 매월 반복

### 시나리오 5 — 공항 픽업 배정 & 수행 (서비스 파트너)
1. **운영팀**: 배치(또는 예약) 상세 → 서비스 → **서비스 추가**(공항픽업, 도착일·시간, 가격 $50)
2. **운영팀**: 서비스 파트너(드라이버) 지정 → 작업이 service-host-portal에 표시
3. **드라이버**: "내 작업"에서 픽업 정보(학생명·도착지·공항·시간·금액) 확인 → 일정 캘린더 확인
4. **드라이버**: 픽업 수행 → `처리중` → `완료` + 현장 사진 업로드
5. **운영팀**: 예약 상세에서 상태·사진 확인 → 과금 시점에 정산 반영
6. ⚠️ 이 작업은 학생·에이전트 화면에 비표시(마스킹)
