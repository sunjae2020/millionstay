# DTO / Request-Response Contracts

> ✅ **T001-RECON-VERIFIED** 2026-04-26 — corroborated by `docs/reverse/_audit/T001_RECON_REPORT.md` §g.


> Most DTOs are auto-generated by **Orval** from the OpenAPI spec into `lib/api-zod/src/generated/api.ts` (~3900 lines). The frontend consumes typed React Query hooks from `lib/api-client-react`.

## Conventions in use

- Naming: `Create<Entity>Body`, `Update<Entity>Body`, `List<Entity>QueryParams`, `<Entity>Response`.
- Validation: All `POST` / `PUT` / `PATCH` use `Schema.safeParse(req.body)` (`req.params` / `req.query` similarly).
- Error response — **two** shapes are in use; this is inconsistent:
  - Most routes: `{ "error": "<message>" }`
  - Auth middleware: `{ "success": false, "error": { "code": "UNAUTHORIZED", "message": "..." } }`
- Success response — **no** standard envelope. Most lists return raw arrays; details return raw objects.
- No standard pagination response shape. Pagination is by query params (`?page=1&limit=20`); pagination metadata, when included, is added ad-hoc.

## Auth DTOs

```ts
interface LoginBody { email: string; password: string; }

interface LoginResponse {
  // Admin
  token: string;                       // access JWT (8h)
  user: { id: number; email: string; role: string; first_name: string; last_name: string };
  // Refresh token is set as an httpOnly cookie (not in response body)
}

interface PartnerLoginResponse {
  token: string;                       // partner JWT (7d)
  user: { id: number; email: string; portal_type: "agent" | "owner"; account_id: number };
}

interface GuestLoginResponse {
  token: string;                       // ⚠️ NOT `access_token` — keep in mind for clients
  user: { id: number; email: string; account_id: number; first_name: string; last_name: string };
}
```

## C# migration risks (DTO layer)

| Pattern | Severity | Detail |
|---|---|---|
| Numeric fields serialized as **strings** (`invoices.amount`) | 🟡 Medium | Need explicit `JsonConverter` for `decimal` in C# DTO; the contract is "string in JSON, decimal in code" |
| Two error response shapes | 🔴 High | Standardize before migrating — pick one (recommend the structured `{success,error:{code,message}}`) |
| List endpoints return raw arrays, no pagination metadata | 🟡 Medium | Fine for EF/.NET but front-end pagination relies on `Content-Range` or implicit count — needs explicit envelope going forward |
| Guest token field is `token` not `access_token` | 🟢 Low | Trivial — but inconsistent with OAuth conventions |
| Snake_case JSON fields throughout | 🟢 Low | Use `[JsonPropertyName]` or `JsonNamingPolicy.SnakeCaseLower` (ASP.NET 8+) |
